CONCEPT EXPLAINER

🐳 Docker Compose, Explained

How one YAML file defines, configures, and runs your whole multi-container application with a single command.

1What is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications. Instead of typing long docker run commands for each service — with all their ports, volumes, environment variables, and networks — you describe everything once in a compose.yaml file, then start the entire stack with one command.

One-sentence summary: Compose = infrastructure as code for local/staging environments. Your whole app (web server, database, cache, workers) becomes a version-controlled, one-command setup.

🧩 Declarative

You declare the desired state in YAML; Compose figures out create, start, and ordering steps.

📦 Multi-service

Web + DB + cache + queue on one isolated network, wired together automatically via service names.

♻️ Repeatable

Same file = same environment on every teammate's machine and CI runner. Kills "works on my machine".

2Without vs. With Compose

# ❌ WITHOUT Compose — long, error-prone, must be repeated manually & in the right order
docker network create mynet
docker volume create dbdata
docker run -d --name db --network mynet -v dbdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name web --network mynet -p 8000:8000 \
  -e DATABASE_URL=postgres://postgres:secret@db:5432/app myapp:latest
# ...and rebuild/restart each by hand after every change

# ✅ WITH Compose — one file, one command
docker compose up

3Anatomy of a compose.yaml

services:                          # ← the containers of your app
  web:                             # service name (also its DNS name on the network!)
    build: .                       # build image from ./Dockerfile
    ports:
      - "8000:8000"                # host:container port mapping
    environment:
      - DATABASE_URL=postgres://postgres:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy # wait until db passes its healthcheck
    volumes:
      - ./src:/app/src             # bind mount: live code reload
    restart: unless-stopped

  db:
    image: postgres:16             # pull a prebuilt image instead of building
    environment:
      - POSTGRES_PASSWORD=secret
    volumes:
      - dbdata:/var/lib/postgresql/data  # named volume: data survives restarts
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

volumes:                           # declare named volumes
  dbdata: {}

networks:                          # (optional) Compose creates a default one automatically
  default: {}
Key magic: every service joins a shared network, so your app connects to the database using the hostname db (the service name) — no IPs, no linking.

5Runtime architecture

Only web publishes a port to the host; db and redis stay private inside the network — reachable only by sibling containers. That's the security model in one picture.

6Essential commands

CommandWhat it does
docker compose up -dStart everything in the background
docker compose up --buildRebuild images, then start
docker compose downStop & remove containers + network (-v also deletes volumes/data!)
docker compose ps / logs -f webSee status / follow one service's logs
docker compose exec web shOpen a shell inside a running container
docker compose restart web / pullRestart one service / refresh images
docker compose -f base.yaml -f prod.yaml upLayer multiple config files (override wins)

7Key concepts at a glance

Project = folder

Compose groups everything under a "project name" (default: the folder name). All containers get prefixes like myapp-web-1. Override with -p myproject or name: in the file.

depends_on ≠ "database is ready"

Plain depends_on only controls start order. Use condition: service_healthy plus a healthcheck to wait for the DB to actually accept connections.

bind mounts vs. named volumes

./src:/app/src → live host folder (great for dev hot-reload). dbdata:/var/lib/... → Docker-managed volume (great for durable data). Never bake data into image layers.

Variables & multiple environments

${VAR} interpolates from your shell or a .env file next to the YAML. Common pattern: base compose.yaml + compose.override.yaml (auto-loaded for dev) + compose.prod.yaml.

Profiles

Tag services with profiles: [debug]; they only start with --profile debug. Handy for optional tooling like admin UIs.

scale

docker compose up -d --scale worker=4 runs multiple replicas; Compose load-balances by DNS round-robin.

8Compose vs. plain Docker vs. Kubernetes

docker runDocker ComposeKubernetes
DefinitionCLI flags per containerOne YAML fileMany manifest YAMLs
Scale1 containerOne host, many containersMulti-node cluster
Self-healing / orchestration—Limited (restart policy)Full (rescheduling, autoscaling, rollouts)
Best forQuick one-offsLocal dev, CI, single-server staging/small prodProduction at scale
Rule of thumb: Compose is a local & CI workhorse, not a cluster orchestrator. Don't expect multi-host scheduling, service discovery across nodes, or advanced rollouts.
